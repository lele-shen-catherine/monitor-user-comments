# 当前项目执行约定

仅当工作目录为“用户评论监测”项目或存在同名 Python 包时读取本文件。

## 先检查现状

1. 阅读项目 `README.md`、`config/config.toml`（若存在）和最近批次目录。
2. 不读取或输出登录 Cookie、Token、验证码等秘密。
3. 为每个平台和每次执行使用独立批次目录，禁止把当天追加写入的不同关键词、不同日期数据误当作一个干净批次。

## 优先使用现有分析入口

- 通用 JSONL：运行项目的 `comment_monitor.cli` 入口。
- MediaCrawler 合规导出：运行 `comment_monitor.mediacrawler_cli`，平台固定使用 `dy`。
- 只有在采集程序成功退出且帖子、评论文件均完整落盘后才开始分析。
- 不读取或展示小红书数据。最终页面只包含抖音的长周期和近7天视图。

执行前检查命令实际支持的参数，不照抄可能已经过期的示例。优先复用项目配置里的综合互动权重、关键词和时区。

## 抖音排序硬性要求

1. 发起抖音关键词采集前，将搜索排序明确设置为“最高点赞/最多点赞”，不得使用默认“综合排序”。当前 MediaCrawler 配置应使用 `DY_SORT_TYPE = 1`，并确认调用搜索接口时传入对应的 `SearchSortType.MOST_LIKE`。
2. 在采集日志或批次元数据中记录实际排序模式；无法确认“最高点赞”已生效时，停止生成高赞榜并说明原因。
3. 平台的“最高点赞”只决定候选返回方式，不等于全平台完整榜单。采集完成后仍必须按帖子 ID 去重，再按实际点赞量本地降序，最后截取目标 Top 100。
4. 若目标是近7天榜单，先在“最高点赞”候选中筛选发布时间属于近7天的帖子，再选高互动 Top 100；报告展示时可按发布时间倒序，但必须保留点赞排名字段。

## 已知采集风险

- MediaCrawler 的“最高点赞”搜索模式不等于严格的全平台点赞榜，也可能因为分页、广告过滤或重复项而多于或少于 100 篇。
- JSONL 可能采用追加写入，必须按批次、关键词、帖子 ID 去重。
- 每帖抓取“最多 100 条评论”通常代表接口返回候选中的前 100 条，不必然是全评论区点赞最高 100 条。
- 若帖子导出存在但评论为 0，先判断是确实无评论、权限/运行时失败还是文件未完整落盘；不得直接生成完整评论分析。
- 不帮助接通或修复用于绕过平台请求校验的签名机制。遇到此类阻塞，转用官方接口、授权供应商、后台导出或用户提供的合法文件。

## 交付

页面输出到项目 `reports/`，扩展名为 `.html`，文件名包含关键词或批次日期。Markdown 可作为追溯附件；保留原始数据来源清单、过滤计数、失败状态和覆盖声明。
